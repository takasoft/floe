# Floe benchmarks

Reproducible performance harnesses for Floe's refresh engine, plus the numbers
measured on a reference machine. The goal is honest, repeatable figures you can
regenerate locally, not marketing peaks.

All workloads use the quickstart pipeline (a last-mile delivery analytics DAG:
two `silver` enrichments feeding four `gold` rollups) over a synthetic,
foreign-key-consistent dataset generated by `examples/quickstart/seed_sources.py`.
Set `FLOE_SEED_DELIVERIES` to choose the fact-table size; dimensions, safety
events, and defects scale proportionally.

## What is measured

Each run reports two phases:

- **seed**: generate the synthetic source data and append it into bronze Iceberg
  tables (PyIceberg `append`).
- **apply**: run the real Floe refresh path for every dynamic table in
  topological order. Each refresh is a full recompute: PyIceberg scan into
  DuckDB, the table's SQL, then an Iceberg overwrite. No incremental shortcuts.

The numbers therefore reflect a cold, full materialization of the whole DAG, which
is the worst case for Floe; steady-state incremental refreshes touch far less data.

## 1. Native harness (engine only)

Isolates Floe's compute from object storage and Postgres: a local SQLite catalog
and an on-disk warehouse. This is the cleanest measure of the engine itself.

```bash
# from the repo root, inside the project venv
BENCH_DELIVERIES=2000000 python benchmarks/bench_native.py
```

Knobs: `BENCH_DELIVERIES` (fact rows), `BENCH_WORKDIR` (reuse a scratch dir),
`BENCH_KEEP=1` (keep the catalog + warehouse for inspection).

## 2. Containerized stack (production-shaped)

The full Compose stack: MinIO (S3-compatible object store) as the warehouse and
Postgres as the Iceberg catalog, with Floe running in its own container. This
adds real object-store and catalog round-trips, so it is slower than native and
more representative of a deployment.

```bash
# choose a dataset size, then run seed + apply
export FLOE_SEED_DELIVERIES=2000000
docker compose up -d minio postgres
docker compose up minio-init
docker compose run --rm floe-seed
docker compose run --rm --no-deps floe-apply
```

`FLOE_SEED_DELIVERIES` and the related `FLOE_SEED_*` knobs are documented in
`.env.example`.

## 3. Cross-engine read/write (experimental Flink profile)

Demonstrates that Floe writes plain Apache Iceberg: a Flink SQL job reads a
Floe-authored `silver` table and writes a new `gold` table back into the SAME
catalog and warehouse, which Floe can then read. See the `flink` profile in
`docker-compose.yml` and `docker/flink/`.

```bash
docker compose --profile flink up -d flink-jobmanager flink-taskmanager
docker compose --profile flink run --rm --no-deps flink-sql
```

## Reference results

Machine: Windows 11 host, 16 logical CPUs, 64 GB RAM. Native runs used the host
Python venv; containerized runs used Docker Engine inside WSL2 (Ubuntu). Single
process, default configuration, warm OS page cache. Your numbers will vary with
hardware, disk, and Docker resource limits.

### Native, full DAG materialization

| deliveries | seed   | apply  | end-to-end | peak RSS |
| ---------: | -----: | -----: | ---------: | -------: |
|  2,000,000 |  4.1 s |  6.0 s |    10.2 s  |  1.49 GB |
|  5,000,000 |  9.0 s | 10.4 s |    19.3 s  |  2.46 GB |

The dominant `apply` cost is `silver.deliveries_enriched`, the full join of the
fact table against the DA and route dimensions: at 5M rows it sustains roughly
700k rows/s through the scan, join, and Iceberg overwrite.

### Containerized (MinIO + Postgres), 2,000,000 deliveries

seed 8.6 s, apply 13.0 s. Per dynamic table during apply:

| dynamic table                  |     rows | duration |
| ------------------------------ | -------: | -------: |
| silver.deliveries_enriched     | 2,000,000 | 3,613 ms |
| silver.safety_events_enriched  |  159,350 |   765 ms |
| gold.delivery_quality_daily    |      600 | 1,127 ms |
| gold.da_daily_performance      |   61,983 |   957 ms |
| gold.regional_safety_summary   |       96 |   408 ms |
| gold.station_daily_summary     |    1,240 |   382 ms |

Pure refresh work sums to about 7.3 s; the remainder is container start, S3, and
catalog round-trips. Row counts match the native run exactly, confirming the
DuckDB-local and MinIO + Postgres backends are equivalent.

### Cross-engine (Flink reads Floe, Floe reads Flink), 2,000,000 deliveries

A one-shot Flink SQL container created an Iceberg `JdbcCatalog` over the same
Postgres `iceberg_tables` that Floe's PyIceberg `SqlCatalog` writes, read
`silver.deliveries_enriched` (2,000,000 rows authored by Floe/DuckDB), and wrote
`gold.flink_da_throughput` (2,000 per-DA rows) back into the shared catalog. Then
Floe read that Flink-authored table back through DuckDB and the top rows matched
Flink's own output, proving bidirectional interop with no copy or conversion.
